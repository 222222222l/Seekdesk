# Seekdesk：事件驱动求职工作流升级方案

2026-11-23 · 规划，**不更改现有投递开关或真实账号操作**。关联 [开发与测试](development.md)。

## 为什么更新

本仓已经把来源采集、去重、模型匹配、人工审阅、申请/沟通回执和通知封装在本地工作台。Swarm 的最有效启发是 **可靠事件交接与休眠恢复**，而不是给每个岗位配置多个会聊天的 Agent。求人岗位的过期、平台验证阻塞、重复申请和误发可能造成实际损失，应优先使用确定性状态机。

| 卡 | 优先级 | 开发内容 | 为什么及验收 |
|---|---|---|---|
| SD-SW0 | P0 | 固定真实状态/权限边界：职位首次见到、确认更新、待核验、推荐、待用户决定、已申请/已拒绝、无法确认 | 避免把重复抓取当新增岗位 |
| SD-SW1 | P0 | 在现有 SQLite 下追加本地 `JobEvent`、稳定 sourceId/jobId/简历版本、事务性去重和事件回放 | 重启后仍可证明为何推荐/为何未联系；100 次重复输入只有一项业务动作 |
| SD-SW2 | P1 | 将采集、匹配、文书建议、用户审批、投递回执建成条件化 DAG；平台登录/验证码暂停本来源，不影响其他来源 | 避免把不可用来源拖成全局卡死 |
| SD-SW3 | P1 | 持久化待办/租约/唤醒，恢复时先查下游已知回执；不由模型自行触发发送简历 | 降低重复投递和失联；回包丢失后能对账 |
| SD-SW4 | P1 | 验证器检查原岗位 URL、岗位有效期、匹配证据、联系方式/附件与用户授权；定向返工 | 匹配评分不是事实核验，敏感动作需显式许可 |
| SD-SW5 | P2 | 无 LLM 的“本周新增、待审、已联系、失败原因”看板与单 Agent 对照 | 降低 Token 消耗，报告必须从本地事件和实际回执生成 |

**优先顺序**：个人求职应用先完成 SD-SW0/1/4 的可信状态与隐私；SD-SW2/3 仅在出现多来源任务阻塞时扩展。保留目前默认关闭的自动联系/投递开关。简历、账号令牌及完整招聘页面不得进入跨项目 OrgOS 共享板；只允许脱敏事件和公开示例。
